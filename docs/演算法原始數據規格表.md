## 1. 資料座標與基本規則

- 一週共 14 個「價位格」，索引 0～13：
  - index 0、1：週日購入價（同一個數字寫兩次，因為程式陣列把週日也算一格但沒有 AM/PM 之分）
  - index 2 = 週一 AM、3 = 週一 PM、4 = 週二 AM、5 = 週二 PM、6 = 週三 AM、7 = 週三 PM、
    8 = 週四 AM、9 = 週四 PM、10 = 週五 AM、11 = 週五 PM、12 = 週六 AM、13 = 週六 PM
  - 這與使用者規格書「四、本週價格輸入」的 12 個時段一一對應（index 2～13）。
- **倍率 (rate)**：所有價格都是「購入價 × 倍率」，倍率以 `RATE_MULTIPLIER = 10000` 的整數尺度內部運算，對外仍以小數表示（例如
  `0.9` 代表 90%）。
- **無條件進位公式**：`price = intceil(rate * buy_price)`，其中
  `intceil(val) = Math.trunc(val + 0.99999)`。
  這不是單純的 `Math.ceil`：它先加上 `0.99999` 再截斷，目的是模擬遊戲原生 32-bit 浮點運算的誤差容忍度，恰好整數的輸入
  仍會得到該整數本身，非整數一律進位到下一個整數。移植時必須完全照抄這個寫法，不能用 `Math.ceil(rate * buy_price)` 取代。
- **反向容錯（fudge factor）**：因為反編譯結果不是 100% 精確重現遊戲的 32-bit ARM 浮點運算，引擎在「找不到任何符合的路徑」時，
  會把每個時段的合法區間上下限各放寬 `fudge_factor`（從 0 開始逐次 +1，最多到 5），直到至少找到一種可能路徑為止。
  這是刻意設計的容錯，不是 bug，第一版就要保留。

## 2. 四種 Pattern 的產生規則

Pattern 編號與使用者規格書的四型別一一對應：

| 編號 | 內部名稱 | 中文名稱 |
| --- | --- | --- |
| 0 | FLUCTUATING | 波動型 |
| 1 | LARGE_SPIKE | 大漲型 |
| 2 | DECREASING | 遞減型 |
| 3 | SMALL_SPIKE | 小漲型 |

### Pattern 0：波動型（Fluctuating）

結構：`高價期1 → 遞減期1 → 高價期2 → 遞減期2 → 高價期3`，五段共 12 格（index 2～13）。

- `decPhaseLen1`：等機率取 `2` 或 `3`（各 50%）；`decPhaseLen2 = 5 - decPhaseLen1`（因此兩段遞減期加總固定為 5 格）。
- `hiPhaseLen1`：`0～6` 之間等機率整數（7 選 1）。
- `hiPhaseLen2and3 = 7 - hiPhaseLen1`；`hiPhaseLen3`：`0 ～ (hiPhaseLen2and3 - 1)` 之間等機率整數。
- `hiPhaseLen2 = hiPhaseLen2and3 - hiPhaseLen3`。
- 高價期每一格：獨立均勻分布 `rate ~ U(0.9, 1.4)`（各格互相獨立，不是連續遞減/遞增）。
- 遞減期：起始 `rate ~ U(0.6, 0.8)`，每往下一格：`rate -= 0.04`，再額外扣 `U(0, 0.06)`（等效每格總遞減量落在 `U(0.04, 0.10)`）。
- 三段長度組合的枚舉機率：`1 / (4-2) / 7 / (7 - hiPhaseLen1)`（即 `decPhaseLen1` 兩選一、`hiPhaseLen1` 七選一、
  `hiPhaseLen3` 在剩餘長度中等機率）。

### Pattern 1：大漲型（Large Spike）

結構：`盤整遞減期 → 五格主高峰 → （若還有剩餘格數）隨機低價期`。

- `peakStart`：`3～9` 之間等機率整數（7 選 1，index 從 3 到 9，即高峰最早出現在週一 PM，最晚在週四 PM 起跳）。
- 高峰前的遞減期（index 2 到 `peakStart-1`）：起始 `rate ~ U(0.85, 0.9)`，每格再扣 `0.03 + U(0, 0.02)`（等效每格遞減量
  `U(0.03, 0.05)`）。
- 主高峰五格（index `peakStart` 到 `peakStart+4`），彼此獨立：
  1. `U(0.9, 1.4)`
  2. `U(1.4, 2.0)`
  3. `U(2.0, 6.0)` ← **真正的最高峰**，理論上限可達購入價 6 倍
  4. `U(1.4, 2.0)`
  5. `U(0.9, 1.4)`
- 高峰之後剩餘格數（若 `peakStart+5 < 14`）：每格獨立 `rate ~ U(0.4, 0.9)`。
- `peakStart` 七種取值等機率，各 `1/7`。

### Pattern 2：遞減型（Decreasing）

結構：整週（index 2～13，共 12 格）連續遞減，沒有反彈。

- 起始 `rate ~ U(0.85, 0.9)`。
- 每格：`rate -= 0.03`，再扣 `U(0, 0.02)`（等效每格遞減量 `U(0.03, 0.05)`）。
- 沒有分段長度需要枚舉，機率固定為 1（此 Pattern 只有一種「形狀」）。

### Pattern 3：小漲型（Small Spike）

結構：`遞減期（可為 0 格） → 兩格緩漲 → 三格小尖峰(帽子形) → （若還有剩餘）遞減期`。

- `peakStart`：`2～9` 之間等機率整數（8 選 1，`1/8`）。
- 高峰前遞減期（index 2 到 `peakStart-1`，`peakStart=2` 時此段長度為 0）：起始 `rate ~ U(0.4, 0.9)`，每格遞減量
  `0.03 + U(0, 0.02)`（同 Pattern 1/2 的遞減公式）。
- 緩漲兩格（index `peakStart`、`peakStart+1`）：各自獨立 `rate ~ U(0.9, 1.4)`。
- 小尖峰三格（index `peakStart+2`、`peakStart+3`、`peakStart+4`），這三格彼此**不獨立**，是同一個 `rate` 衍生出來：
  - 令 `rate ~ U(1.4, 2.0)`（這個 rate 本身也是隨機變數，決定尖峰有多高）。
  - 中間格（`peakStart+3`）＝ `intceil(rate * buy_price)`（尖峰最高點，最高約購入價 2 倍）。
  - 左格（`peakStart+2`）＝ `intceil(U(1.4, rate) * buy_price) - 1`。
  - 右格（`peakStart+4`）＝ `intceil(U(1.4, rate) * buy_price) - 1`。
  - 因為左右兩格都是「在 `[1.4, rate)` 內再抽一次」，它們必然 ≤ 中間格，形成兩側低、中間高的「帽子」形狀。
    移植時這段的機率計算比較複雜（見 vendor 原始碼 `generate_peak_price()`，用到條件機率積分），**必須照抄整個函式邏輯**，
    不能只用簡單的區間相交去估。
- 尖峰之後剩餘格數（若 `peakStart+5 < 14`）：起始 `rate ~ U(0.4, 0.9)`，遞減量同上（`0.03 + U(0, 0.02)`）。

## 3. 上週 Pattern → 本週 Pattern 轉移機率矩陣

若玩家知道「上週的 Pattern」，本週各 Pattern 的先驗機率如下（列＝上週 Pattern，欄＝本週 Pattern，數字為機率）：

| 上週＼本週 | 0 波動型 | 1 大漲型 | 2 遞減型 | 3 小漲型 |
| --- | --- | --- | --- | --- |
| 0 波動型 | 0.20 | 0.30 | 0.15 | 0.35 |
| 1 大漲型 | 0.50 | 0.05 | 0.20 | 0.25 |
| 2 遞減型 | 0.25 | 0.45 | 0.05 | 0.25 |
| 3 小漲型 | 0.45 | 0.25 | 0.15 | 0.15 |

若玩家選「不知道上週型態」，使用穩態機率（steady-state，對整個轉移矩陣取極限分布）：

| Pattern | 機率 | 精確分數 |
| --- | --- | --- |
| 0 波動型 | 34.63% | 4530/13082 |
| 1 大漲型 | 24.74% | 3236/13082 |
| 2 遞減型 | 14.76% | 1931/13082 |
| 3 小漲型 | 25.88% | 3385/13082 |

> 來源備註：這個穩態分布不是隨便估的，是 vendor 原始碼作者依照
> [issue #68](https://github.com/mikebryant/ac-nh-turnip-prices/issues/68) 與
> [PR #90](https://github.com/mikebryant/ac-nh-turnip-prices/pull/90) 的社群驗證結果寫死在程式碼中的常數，移植時原樣照抄即可，
> 不要自己重新計算穩態分布（避免浮點誤差造成兩邊不一致）。

## 4. 週日購入價未知時的處理

- 如果玩家還沒輸入週日購入價（或本來就是遊戲內第一次買大頭菜），演算法會把購入價當成 `90～110` 鈴錢之間的每一個整數
  （21 種等機率可能）都各自展開一次，再疊加上面的 Pattern 枚舉。
- 特殊分支：若旗標 `first_buy`（玩家在該座島「有史以來第一次」買大頭菜，不是單純不知道上週型態）為真，
  展開購入價後**只會枚舉 Pattern 3（小漲型）**，不會呼叫 `generate_all_patterns()` 套用轉移機率矩陣。
  這是 vendor 原始碼裡明確寫死的行為（見 `generate_possibilities()`），第一版先原樣保留這個分支，
  但這屬於「玩家帳號從未買過大頭菜」的極少數情境，UI 上可先不強調、只在演算法內部保留正確性；
  之後如果要在 UI 開放這個選項，要另外跟這份規格表對齊行為，不要自己改寫。

## 5. 從已知價格反推可能路徑的方法（貝氏排除）

每一個「候選路徑」＝（Pattern 編號＋該 Pattern 內部的分段長度／高峰位置等參數）的一種具體組合。對每個候選路徑：

1. 用上述公式算出該路徑下，每個時段「理論最小值／最大值」的區間（`min_pred` / `max_pred`）。
2. 如果玩家在某時段已經輸入實際價格，且該價格落在這個路徑允許的區間外（超出 `fudge_factor` 容差），
   這條候選路徑機率直接歸零、整條路徑被排除——這就是使用者要求的「排除所有不符合的可能曲線」，而不是用
   「連跌三次＝大漲型」這種 heuristic 猜測。
3. 若價格落在區間內，用該價格把這條路徑的機率密度往下修正（乘上「這個精確價格在理論分布中出現的機率密度」），
   並把該時段的 `min_pred = max_pred = 實際價格`（之後這個時段不再有不確定性）。
4. 所有候選路徑跑完一輪後，把「同一個 Pattern 編號」底下所有還存活（機率 > 0）的候選路徑機率加總，
   得到四個 Pattern 的總機率；再除以全部候選路徑機率總和做正規化，得到使用者要看到的
   「🔥 大漲型 62% ／ 📈 小漲型 21% ／ …」百分比。
5. 每個未來時段的「理論可能範圍」＝所有存活路徑在該時段 `min_pred`／`max_pred` 的全域最小值／最大值
   （vendor 原始碼裡 `pattern_number: 4` 那個特殊聚合結果）。
6. 「高機率範圍」（使用者規格書六、要求要與理論範圍分開顯示的那個）**不是** vendor 原始碼現成算好的欄位，
   是我們自己要在 Phase 5 用「依機率加權的路徑集合」另外算的統計量（例如取存活路徑機率加權後的 10%～90%
   分位數），這一步需要新寫程式碼，但仍要用同一組「存活路徑＋各自機率」當輸入，不能另外發明公式。

## 6. 「本週保證最低價／本週可能最高價」的計算方式

- `weekGuaranteedMinimum`：把每個候選路徑「還沒發生、仍是區間」的未來時段取最小值收集起來，再取這些最小值裡的最大值
  （也就是「不管接下來怎麼走，至少能賣到的價錢」）；若玩家已經填到只剩最後一格，改用最後一格的 min/max。
  若中途出現「已經是區間之後又出現一個固定值」，代表玩家跳過了某一格沒填，這條資料要整段重置重新收集
  （vendor 原始碼有這個資料完整性檢查，移植時要保留）。
- `weekMax`：同樣邏輯，收集所有未來時段的最大值，取最大值。
- 頁面上「預測本週可能最高」等數字，來源就是所有存活路徑各自的 `weekMax` 之後再取全域最大值。

## 7. 單元測試比對基準

Phase 3 建立測試時，至少要覆蓋：

- 純遞減型（Pattern 2）：連續 12 格價格單調遞減，且遞減比例落在 `0.85→0.9` 起跳、每格再扣約 3%～5% 的範圍內。
- 已知大漲型峰值三格（例如某時段價格達購入價 4～5 倍）：驗證只有 Pattern 1 存活，且峰值位置被正確鎖定在
  `2.0～6.0` 倍那一格。
- 小漲型帽子形狀：中間格 ≥ 左右兩格。
- 轉移機率矩陣：給定「上週＝大漲型」，本週初始（尚無本週資料）的四個 Pattern 機率應直接等於矩陣第 1 列
  （0.50 / 0.05 / 0.20 / 0.25），可以拿來當最簡單的 smoke test。
- 交叉驗證：用同一組輸入（購入價＋任意幾格已知價格）手動貼到 Turnip Prophet 官方網站
  （<https://turnipprophet.io/>），比對兩邊算出的 Pattern 機率與價格區間應該一致（容許極小的浮點誤差）。
